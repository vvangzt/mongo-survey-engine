# 5. AI 使用日志与说明（修订版）

本文件替代早期仅按一般开发经验整理的 AI 日志。以下记录按第一阶段实际迭代整理：
Prompt 为当时需求的摘要，Result 对应 AI 实际给出的方案或代码方向，Modify 对应我
在评审、联调和测试后真正做出的修改。技术结论以最终代码和测试结果为准。

## 5.1 AI 使用日志

### 记录 1：数据库集合、版本模型与三套 Schema

- **工具名称**：DeepSeek (via Zcode)
- **Prompt（提示词）**：
  > 为一个类似问卷星的在线问卷系统设计 MongoDB 集合，要求用户只能查看自己创建的问卷，
  > 支持发布状态、截止时间、匿名填写、动态跳转、高并发答卷和统计；请说明题目和答卷
  > 应该内嵌还是引用，如何避免 16 MB 限制，并给出 JSON Schema、Pydantic 和 Mongoose 定义。
- **Result（AI 给出的初始方案/代码摘要）**：
  AI 提出了 `users`、`surveys`、`survey_versions`、`responses` 的拆分，建议将题目、
  选项、校验和跳转规则内嵌到问卷版本，将一次提交的全部答案内嵌在一个答卷文档；
  给出了 JSON Schema、Pydantic 和 Mongoose 三套结构，以及唯一索引和复合索引建议。
  该方案的主体方向是正确的，但它同时并列三套技术栈，没有说明哪一套是实际运行入口。
- **Modify（我发现的问题及做出的修改）**：
  1. 确定实际运行栈为 FastAPI + Pydantic + PyMongo，Mongoose 仅作为结构参考，避免两套
     ORM 都被误认为运行代码；
  2. 保留不可变 `survey_versions`，并明确 `responses` 固定引用答题时的版本；
  3. 增加 `backend/database.py` 和 `backend/init_db.py`，确保索引不是只写在文档里，
     而是在应用启动或显式初始化时真正创建；
  4. 增加 `.env.example`、单机 MongoDB 启动说明，并明确不强制 Docker 或副本集；
  5. 将需求中的“跳转规则”术语兼容到模型：持久化字段仍是 `logic.rules`，模型提供只读
     属性 `jump_rules`，避免维护两份跳转配置；
  6. 对题目数、选项数、文本长度和序列化体积设置上限，明确文档不会无限增长。

  这次修改主要不是推倒 AI 的集合结构，而是把“看起来合理的设计”落成可执行、可部署的
  Schema 和索引约定。

### 记录 2：校验与动态跳转引擎

- **工具名称**：DeepSeek (via Zcode)
- **Prompt（提示词）**：
  > 实现问卷的校验与动态跳转引擎。多选题检查最少/最多/指定数量，数字题检查合法整数和
  > min/max，文本题检查长度；跳转逻辑必须配置在数据中，支持单选、多选、数字比较。
  > 请设计 `evaluate_next_question(current_question, user_answer) -> next_question_id`，
  > 并便于以后扩展 `contains`、`not_in` 等运算符。
- **Result（AI 给出的初始方案/代码摘要）**：
  AI 生成了校验函数、跳转规则和运算符处理，并提供了二参数形式的跳转函数。
  初版把结果表示为“目标题目 ID 或 `None`”，条件上下文和规则状态没有完全显式化。
  这个接口在只问“有没有跳转目标”的单元测试里能通过，但 `None` 既可能表示正常下一题，
  也可能表示问卷结束；复杂分支下容易产生调用方误判。部分逻辑还分散在模型校验和接口层。
- **Modify（我发现的问题及做出的修改）**：
  1. 将跳转结果改为显式的 `JumpDecision(action=goto/next/end)`，并提供 `SurveyEnded`
     作为便利函数的控制信号；
  2. 增加 `prior_answers` 上下文，让引用前序题目的条件可以被正确评估；
  3. 将条件统一为 `ConditionGroup(mode=all/any)`，限制条件只能引用当前或更早的题；
  4. 限制 `goto` 只能向后，发布时校验目标存在且不形成环；
  5. 将运算符抽成注册表，默认支持单选、多选、数字比较，并用扩展测试验证
     `contains` 的插件式注册方式；
  6. 增加服务端 `/next` 接口。前端不再自己决定分支，而是提交当前答案后由服务端计算
     下一道可见题目；
  7. 提交时重新遍历完整路径，拒绝隐藏题目的答案和未满足的必答题。

  最终，跳转 DSL、校验函数和路径重放位于 `schemas/pydantic/`，整个流程有单元测试和
  真实 HTTP 测试覆盖。

### 记录 3：统计聚合与空数据契约

- **工具名称**：DeepSeek (via Zcode)
- **Prompt（提示词）**：
  > 为整份问卷和单道题实现统计 API。单选题统计每个选项人数和总作答人数，多选题将
  > option_ids 打平后统计频次，文本题分页列出回答，数字题计算平均值、最大值和最小值；
  > 请使用 MongoDB 原生 `$unwind`、`$group`、`$facet` 聚合管道并给出 FastAPI Controller。
- **Result（AI 给出的初始方案/代码摘要）**：
  AI 给出了按版本过滤的 `$facet` 总览管道：选择题单独统计作答人数，多选展开选项统计
  频次，数字题使用 `$avg/$min/$max`，文本题同时返回总数和分页结果；还给出了单题详情的
  `$filter + $facet` 管道。代码已经有补零和空数字题返回空值的处理，但最初的测试和
  文档主要集中在有数据的正常路径，没有把无答卷、无文本答案、无发布版本和校验失败
  不落库全部列为验收条件；单题聚合所需的 `answers.question_id` 复合索引也是后补的。
- **Modify（我发现的问题及做出的修改）**：
  1. 明确统计只针对“当前已发布版本”，避免把不同版本的题目定义混合；
  2. 多选的选项频次和“回答本题人数”分开，不能用选项次数之和冒充人数；
  3. 选项按版本定义补零，数字题无答案时返回 `answered_count=0` 和 `average/min/max=null`；
  4. 文本题用 `$facet` 同时返回总数与分页，限制 `page_size <= 100`；
  5. 增加 `(survey_id, survey_version_id, answers.question_id)` 索引；
  6. 对未发布版本返回 409，对无权限或不存在返回 404；
  7. 增加真实 MongoDB 数据验证、零数据测试、无效提交不落库测试和 30 并发提交测试。

  这次修改把统计从“正常数据下结果正确”提升为“空数据、异常提交和多用户场景也有明确
  语义”。

### 记录 4：系统测试、真实认证与问卷生命周期

- **工具名称**：DeepSeek (via Zcode)
- **Prompt（提示词）**：
  > 编写问卷系统的系统测试用例，覆盖创建问卷、添加题目、跳转、校验、正常/匿名提交和
  > 统计；使用 pytest + requests 或等价 HTTP 客户端，测试要能重复运行。
  > 之后开始补全项目，并保证旧功能不退化。
- **Result（AI 给出的初始方案/代码摘要）**：
  AI 先搭建了真实的 Uvicorn + 临时 MongoDB 集成测试框架，覆盖了六类场景；但由于当时
  系统还没有真实登录注册，测试夹具用 `X-Test-User-Id` 请求头和 FastAPI 依赖覆盖注入
  用户身份。这个做法能让测试变绿，但它掩盖了一个真实交付缺口：生产入口没有真正的账号
  体系，用户模型也缺少 PDF 明确要求的 `username` 字段。另有一次接口错误映射重构
  误删了创建问卷路由，集成测试立即暴露出 405，而单元测试没有发现。
- **Modify（我发现的问题及做出的修改）**：
  1. 新增真实注册/登录/退出/当前用户接口，使用 Argon2id 密码哈希和 JWT；
  2. 登录同时设置 HttpOnly Cookie 并返回 Bearer Token；
  3. 在 `users` 中增加唯一 `username`，保留唯一 email；
  4. 删除测试专用身份覆盖，测试夹具改为注册独立用户并保留 Cookie；
  5. 增加越权访问、未登录访问、重复用户名、错误密码、退出后失效等测试；
  6. 补全问卷列表、详情、修改、关闭、整份草稿保存和幂等发布；
  7. 修复错误映射重构中误删的创建路由，并重新执行全部回归测试；
  8. 增加关闭后拒绝提交、一次性提交限制、公开 Slug 填写、分支路径和页面的 HTTP 测试。

  这次修改说明：**测试通过不等于系统完成**。当测试绕过真实认证时，测试结果不能直接
  作为产品可用的证据；只有把认证、权限和生命周期纳入真实链路，集成测试才有意义。

### 记录 5：前端补全与真实浏览器验收

- **工具名称**：DeepSeek (via Zcode)
- **Prompt（提示词）**：
  > 开始为我补全项目，使系统可以真正演示：登录、问卷工作台、问卷编辑器、公开填写和
  > 统计页面都要可用，同时保持后端跳转和校验为服务端权威。
- **Result（AI 给出的初始方案/代码摘要）**：
  在补全前，项目主要是 API 和后端服务，没有可以交给老师直接操作的页面，也没有
  `/survey/{slug}` 的可视化填写流程。AI 随后给出了 Jinja2 + 原生 JavaScript 的轻量前端
  方案，以及问卷列表、编辑器、填写页和统计页的结构。初期页面验证时，跳转规则摘要
  显示的是选项 ID 而不是选项文案，说明仅靠后端测试无法发现前端展示问题。
- **Modify（我发现的问题及做出的修改）**：
  1. 增加登录/注册、工作台、编辑器、公开填写和统计页面；
  2. 填写页通过服务端 `/next` 获取下一题，避免在前端复制一套跳转逻辑；
  3. 增加多选题数量提示、数字/文本校验提示和匿名提交选择；
  4. 在真实浏览器中完成“注册 → 创建 → 编辑 → 保存 → 发布 → 填写 → 提交 → 查看统计”
     的完整流程；
  5. 根据浏览器验收修复规则摘要的选项文案显示，并补充页面/静态资源测试；
  6. 采用单机 MongoDB，不引入 Docker、副本集或 Playwright 作为运行前提；
  7. 已发布版本内容保持冻结；允许从已发布版本克隆新草稿并发布 vN+1，旧版本和旧答卷保留。

  最终页面可以独立演示，前端仅负责展示和收集输入，服务端仍然决定路径、校验和统计口径。

## 5.2 AI 使用说明

### 5.2.1 AI 帮了什么

1. 快速给出多集合、版本化和内嵌/引用策略的候选方案，显著缩短了数据建模阶段；
2. 同时生成 JSON Schema、Pydantic、Mongoose 和示例数据，便于比较结构；
3. 生成校验、跳转、路径重放和统计聚合的第一版代码，尤其是 `$facet`、`$unwind`、
   `$filter` 等 MongoDB 管道的组合；
4. 生成 pytest、requests、临时 MongoDB 和 Uvicorn 的测试骨架，以及页面和文档初稿；
5. 在需求变化时快速给出增量修改，而不是要求从零重写。

### 5.2.2 AI 做错了什么、有哪些局限

1. **接口语义不够明确**：`evaluate_next_question` 初版用目标 ID/`None` 表示结果，
   没有区分下一题、跳转目标和结束问卷；
2. **跨层规则容易漂移**：同一套校验分布在 JSON Schema、Pydantic、Mongoose 和接口层时，
   AI 容易让不同层出现细节差异；Mongoose 的数组校验器在覆盖时曾丢失唯一性检查；
3. **测试可能绕过真实系统**：早期集成测试用伪造用户头获得绿色结果，掩盖了真实注册登录
   和用户名要求的缺失；
4. **容易低估空数据和异常路径**：统计和响应模型在正常数据下正确，但零回答、无发布版本、
   无效提交不落库、文本空页等场景需要人工补充验收；
5. **重构可能出现回归**：错误映射重构曾误删创建路由，单元测试未发现，HTTP 集成测试
   立即发现了 405；
6. **只做后端不等于完成项目**：如果没有明确要求，AI 会停留在 API 层，前端、真实认证和
   公开填写这些交付必需部分需要人工补全；
7. **AI 日志的真实性需要人工负责**：早期日志更接近一般化总结，不能把它当成实际对话
   记录；最终报告应使用真实 Prompt、真实失败结果和实际修改证据。

### 5.2.3 自己改了什么

- 将裸跳转结果改为 `JumpDecision`，并实现服务端 `/next` 与提交路径重放；
- 统一答案校验和错误码，补充多选边界、数字范围、文本长度、隐藏分支答案测试；
- 修复 Mongoose 校验器覆盖导致的问题；
- 将统计限定在发布版本，补上零值、空值、分页和索引；
- 增加真实注册登录、JWT Cookie、Argon2id、用户所有权检查；
- 补全问卷列表、关闭、幂等发布、草稿整份保存和一次性提交策略；
- 增加公开 Slug 页面、前端工作台/编辑器/填写/统计页面；
- 修复浏览器验收发现的规则文案显示问题；
- 把测试从伪造身份改为真实账号，并增加到 64 项自动化测试；
- 在最终优化中补上数字整数开关/小数、精确多选、多选和数字跳转、
  发布后运营设置和新版本发布流程；
- 更新项目说明、API 文档、测试用例表和测试报告。

### 5.2.4 自己设计了什么

1. **聚合边界**：`surveys` 管生命周期，`survey_versions` 保存不可变题目快照，
   `responses` 一份提交一个文档；
2. **版本一致性**：发布版本冻结，答卷固定引用版本，统计按版本计算；
3. **跳转的权威性**：规则存数据和版本中，浏览器不让自行构造路径，服务端最终重算；
4. **单机可运行的一致性策略**：发布使用幂等状态推进，不强制副本集事务；
5. **权限和隐私边界**：管理端按 `owner_id` 强制隔离，匿名答卷不保存身份；
6. **测试边界**：单元测试验证规则，真实 HTTP 测试验证认证/生命周期/公开填写，
   浏览器冒烟验证实际页面；
7. **部署边界**：不强制 Docker/副本集/Playwright，保证评分环境能运行。

### 5.2.5 反思

AI 对“写出可运行的初稿”很有帮助，但它不会自动替人决定数据边界、状态含义和验收标准。
本项目真正关键的修改都来自人工追问：

- `None` 到底代表下一题还是结束？
- 多选题的“总回答人数”能不能用选项次数相加？
- 测试用了伪造身份，为什么生产用户仍无法登录？
- 后端接口全部通过，为什么老师打开页面仍然无法填写？
- 统计结果很好，但空问卷、无发布版本时返回什么？

最终的系统由 AI 初稿、人工架构判断、真实 MongoDB 测试和浏览器验收共同完成。
当前 64 项自动化测试通过，完整流程已在真实浏览器中走通。提交前仍应继续核对 AI 日志中
的 Prompt 和代码片段与实际聊天记录是否一致，并保存必要的测试输出和截图作为证据。
